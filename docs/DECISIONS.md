# Решения и допущения

Что я решил сам там, где ТЗ допускает разные трактовки, и чего нет в этой версии.

## Бизнес-правила

1. **Роль хранится в таблице `profiles`, а не в `user_metadata`.** `user_metadata` пользователь может поменять сам через `supabase.auth.updateUser()`, поэтому для прав это дыра. Менять `profiles` пользователи не могут. Это проверяется отдельным тестом.
2. **Исполнитель обязателен.** Задачу без исполнителя никто не сможет взять в работу (по ТЗ это делает только назначенный исполнитель), поэтому поле обязательное.
3. **Исполнителем можно назначить только сотрудника с ролью «Исполнитель».** Постановщика или несуществующий id база не примет.
4. **Принять или вернуть задачу может любой постановщик, не только автор.** В ТЗ сказано «постановщик» без уточнения. Ограничить автором — одна строка в матрице переходов.
5. **«Принята» — финальный статус.** Других переходов из неё в ТЗ нет, а «другие переходы запрещены».
6. **Комментарий обязателен только при возврате на доработку.** К остальным действиям его можно добавить по желанию, он тоже попадёт в историю. Комментарий из одних пробелов не принимается.
7. **Создание задачи — первая запись в истории (— → «Новая»).** ТЗ включает этот переход в таблицу статусов.
8. **Постановщик может редактировать задачу в любом статусе:** название, описание, объект, исполнителя. Статус меняется только кнопками действий.
9. **Переназначение задачи.** Прежний исполнитель сразу теряет к ней доступ, новый видит всю историю. Профили других исполнителей исполнителю не видны, поэтому в истории действия прежнего исполнителя подписаны «Предыдущий исполнитель».
10. **Удаление — это пометка, а не стирание (soft delete).** Если физически удалять задачу, вместе с ней пропала бы история, а её по ТЗ удалить нельзя. Поэтому удалённые объект или задача пропадают из интерфейса и API у всех, но остаются в базе вместе с историей и отметкой, кто и когда удалил. Вместе с объектом удаляются и его задачи. Физически удалить что-либо через API нельзя никому.
11. **Что видит исполнитель:** свои задачи, объекты, где у него есть задачи (в карточке объекта — только свои задачи), историю своих задач, себя и постановщиков. Других исполнителей не видит.
12. **Учётные записи заводит администратор.** Профиль с ролью создаёт `scripts/seed.ts` или SQL (см. README). Пользователь, которому не назначили роль, может войти, но видит только экран «Нет доступа» и через API тоже ничего не получает.
13. **Пользователя с задачами или записями в истории удалить нельзя** (внешние ключи). Чтобы закрыть доступ, учётную запись блокируют (ban) в Supabase Auth. Так история не теряет авторов.
14. **Автора, дату создания, статус при создании и время записи в истории проставляет база** (`auth.uid()`, `now()`). Клиент не может их передать: прав на эти колонки у него нет.

## Технические решения

- **Права — в два слоя, оба в Postgres.** `GRANT` определяет, какие таблицы и колонки вообще доступны роли `authenticated`, а RLS — какие строки видит конкретный пользователь. Роль `anon` (запрос без входа) не получает ничего.
- **Статус меняется только функцией `change_task_status()`.** У клиента нет права на `UPDATE` колонки `status`. Дополнительно стоит триггер, который отклоняет смену статуса вне функции даже для `service_role` и администратора БД. Функция блокирует строку задачи (`FOR UPDATE`), поэтому два одновременных запроса не пройдут проверку по одному и тому же старому статусу.
- **Матрица переходов — данные, а не код:** таблица `private.task_transitions`, 5 строк. По ней же функция `get_available_transitions()` отдаёт интерфейсу список кнопок, поэтому интерфейс не может разойтись с базой.
- **История только дописывается.** Права на `INSERT/UPDATE/DELETE` нет ни у пользователей, ни у `service_role`. Триггер запрещает `UPDATE/DELETE/TRUNCATE` даже владельцу таблицы. Пишут в историю только функции базы.
- **Внутренние функции и таблицы лежат в схеме `private`,** которую Supabase не публикует через API.
- **Секретный ключ** используется только в локальном скрипте сида (переменная `SUPABASE_SECRET_KEY` без префикса `VITE_`, поэтому Vite не положит её в бандл). Фронтенд при старте отказывается работать, если ему по ошибке подсунули секретный ключ. Файлы `.env*` в git не попадают.
- **Сид работает через настоящий API** от имени сотрудников, поэтому демо-история настоящая. Её даты — реальное время запуска сида, подделать их нельзя.
- **Тесты:** `supabase/tests/database/security.test.sql` — 79 проверок pgTAP прямо в базе от имени разных ролей. `scripts/api-security-check.ts` — 27 «атак» через HTTP API с публичным ключом. Чтобы убедиться, что тесты действительно ловят ошибки, я специально ломал защиту (давал исполнителю видеть все задачи, снимал триггер истории, отключал обязательный комментарий и т. п.) — каждый раз падало от 4 до 19 проверок. UI-сценарии обеих ролей прогонял локально в Playwright.
- **UI:** Ant Design (готовые таблицы, формы и таймлайн на русском), TanStack Query для запросов, React Router. Типы БД сгенерированы `supabase gen types`.

## Чего нет в этой версии (что сделал бы дальше)

- Вложения (фото, акты) к задачам: Supabase Storage с такими же правилами доступа. Для стройки это первое, что попросят.
- Уведомления о смене статуса (email или Telegram).
- Сроки и приоритеты задач, поиск и серверная пагинация. На демо-объёмах фильтрация идёт на клиенте.
- Обновление в реальном времени (Supabase Realtime). Сейчас данные обновляются после действий и при возврате на вкладку.
- Управление сотрудниками и восстановление пароля в интерфейсе. Сейчас это делается через Supabase Dashboard.
- Корзина: просмотр и восстановление удалённых объектов и задач.
- UI-тесты не включены в репозиторий: сценарии обеих ролей я прогонял локально, а в CI имело бы смысл добавить Playwright и `supabase test db`.
