# Решения и допущения

Что я решил сам там, где ТЗ допускает разные трактовки, и чего нет в этой версии.

## Бизнес-правила

1. **Роль хранится в таблице `profiles`, а не в `user_metadata`.** `user_metadata` пользователь может поменять сам через `supabase.auth.updateUser()`, поэтому для прав это дыра. Менять `profiles` пользователи не могут. Это проверяется отдельным тестом.
2. **Исполнитель обязателен.** Задачу без исполнителя никто не сможет взять в работу (по ТЗ это делает только назначенный исполнитель), поэтому поле обязательное.
3. **Исполнителем можно назначить только сотрудника с ролью «Исполнитель».** Постановщика или несуществующий id база не примет.
4. **Принять или вернуть задачу может любой постановщик, не только автор.** В ТЗ сказано «постановщик» без уточнения. Ограничить автором — одна строка в `private.allowed_transitions()`; кнопки и проверка в базе изменятся вместе.
5. **«Принята» — финальный статус.** Других переходов из неё в ТЗ нет, а «другие переходы запрещены».
6. **Комментарий обязателен только при возврате на доработку.** К остальным действиям его можно добавить по желанию, он тоже попадёт в историю. Комментарий без видимого текста — пробелы, переводы строк, неразрывные и «невидимые» символы Юникода — не принимается ни формой, ни базой. То же правило действует для названий и адресов.
7. **Создание задачи — первая запись в истории (— → «Новая»).** ТЗ включает этот переход в таблицу статусов.
8. **Постановщик может редактировать задачу в любом статусе:** название, описание, объект, исполнителя. Статус меняется только кнопками действий.
9. **Переназначение задачи.** Прежний исполнитель сразу теряет к ней доступ, новый видит всю историю. Профили других исполнителей исполнителю не видны, поэтому в истории действия прежнего исполнителя подписаны «Предыдущий исполнитель».
10. **Удаление — это пометка, а не стирание (soft delete).** Если физически удалять задачу, вместе с ней пропала бы история, а её по ТЗ удалить нельзя. Поэтому удалённые объект или задача пропадают из интерфейса и API у всех, но остаются в базе вместе с историей и отметкой, кто и когда удалил. Вместе с объектом удаляются и его задачи — даже если кто-то в ту же секунду добавляет в него новую. Физически удалить что-либо через API нельзя никому, в том числе с секретным ключом.
11. **Что видит исполнитель:** свои задачи, объекты, где у него есть задачи (в карточке объекта — только свои задачи), историю своих задач, себя и постановщиков. Других исполнителей не видит.
12. **Учётные записи заводит администратор.** Профиль с ролью создаёт `scripts/seed.ts` или SQL (см. README). Пользователь, которому не назначили роль, может войти, но видит только экран «Нет доступа» и через API тоже ничего не получает — ни задач, ни объектов, ни сотрудников.
13. **Пользователя с задачами или записями в истории удалить нельзя** (внешние ключи). Чтобы закрыть доступ, учётную запись блокируют (ban) в Supabase Auth. Так история не теряет авторов.
14. **Автора, дату создания, статус при создании и время записи в истории проставляет база** (`auth.uid()`, `now()`). Клиент не может их передать: прав на эти колонки у него нет.
15. **«Выйти» завершает сеанс только на этом устройстве.** Сеансы того же сотрудника на других устройствах не обрываются, а выход срабатывает даже без сети.

## Технические решения

- **Права — в два слоя, оба в Postgres.** `GRANT` определяет, какие таблицы и колонки вообще доступны роли `authenticated`, а RLS — какие строки видит конкретный пользователь. Роль `anon` (запрос без входа) не получает ничего.
- **Статус меняется только функцией `change_task_status()`.** У клиента нет права на `UPDATE` колонки `status`. Дополнительно стоит триггер, который отклоняет любой прямой `UPDATE` статуса в обход функции. Функция блокирует строку задачи (`FOR UPDATE`), поэтому два одновременных запроса не пройдут проверку по одному и тому же старому статусу.
- **Матрица переходов — данные, а не код:** таблица `private.task_transitions`, 5 строк. По ней же функция `get_available_transitions()` отдаёт интерфейсу список кнопок, поэтому интерфейс не может разойтись с базой. Карточка задачи получает задачу и доступные действия одним запросом, так что статус и кнопки на экране всегда согласованы.
- **История только дописывается.** У ролей API, включая `service_role`, нет прав на запись в неё; пишут в историю только функции базы. Триггер дополнительно отклоняет `UPDATE/DELETE/TRUNCATE` от владельца таблицы — на случай ошибки в коде.
- **Секретный ключ урезан.** `service_role` обходит RLS, поэтому ему оставлено только чтение и создание профилей (это нужно сиду). Даже с ним через API нельзя создать или изменить задачу, сменить статус, подделать историю или что-то удалить.
- **Модель угроз — как в ТЗ: «через API».** Администратор базы с прямым SQL-доступом технически может выключить любую защиту внутри Postgres (триггеры, проверки). От этого защищает доступ к самой базе, а не код приложения.
- **Граничные случаи, закрытые отдельно и покрытые тестами:** комментарий из невидимых символов; гонка между удалением объекта и созданием задачи в нём (блокировка строки объекта); исполнитель не может по тексту ошибки узнать, существует ли чужой объект или сотрудник.
- **Внутренние функции и таблицы лежат в схеме `private`,** которую Supabase не публикует через API.
- **Секретный ключ** используется только в локальном скрипте сида (переменная `SUPABASE_SECRET_KEY` без префикса `VITE_`, поэтому Vite не положит её в бандл). Фронтенд при старте отказывается работать, если ему по ошибке подсунули секретный ключ. Файлы `.env*` в git не попадают.
- **Сид работает через настоящий API** от имени сотрудников, поэтому демо-история настоящая. Её даты — реальное время запуска сида, подделать их нельзя.
- **Тесты:** `supabase/tests/database/security.test.sql` — 88 проверок pgTAP прямо в базе от имени разных ролей; проходят и на пустой базе, и с демо-данными. `scripts/api-security-check.ts` — 29 «атак» через HTTP API с публичным ключом. Чтобы убедиться, что тесты действительно ловят ошибки, я специально ломал защиту (давал исполнителю видеть все задачи, снимал триггер истории, отключал обязательный комментарий, возвращал права `service_role` и т. п.) — каждый раз падали соответствующие проверки. UI-сценарии обеих ролей прогонял локально в Playwright.
- **UI:** Ant Design (готовые таблицы, формы и таймлайн на русском), TanStack Query для запросов, React Router. Типы БД сгенерированы `supabase gen types`. Без сети интерфейс показывает предупреждение и сам дозагружает данные, когда связь появится.

## Чего нет в этой версии (что сделал бы дальше)

- Вложения (фото, акты) к задачам: Supabase Storage с такими же правилами доступа. Для стройки это первое, что попросят.
- Уведомления о смене статуса (email или Telegram).
- Сроки и приоритеты задач, поиск и серверная пагинация. На демо-объёмах фильтрация идёт на клиенте.
- Обновление в реальном времени (Supabase Realtime). Сейчас данные обновляются после действий и при возврате на вкладку.
- Журнал изменений полей задачи (кто поменял название или исполнителя). По ТЗ в историю пишется только смена статуса.
- Управление сотрудниками и восстановление пароля в интерфейсе. Сейчас это делается через Supabase Dashboard, а на своём сервере — через Admin API с service_role-ключом (см. README).
- Корзина: просмотр и восстановление удалённых объектов и задач.
- UI-тесты не включены в репозиторий: сценарии обеих ролей я прогонял локально, а в CI имело бы смысл добавить Playwright и `supabase test db`.
